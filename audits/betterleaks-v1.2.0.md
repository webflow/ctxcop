# Audit: `github.com/betterleaks/betterleaks` @ v1.2.0

**Audited:** 2026-05-20 by Andrew Rose (Webflow Cloud Security)
**Tag SHA:** `296fee33358904c47d094fa6716347b223b2c13f` (verified against GitHub API ref; `git tag -v` confirmed lightweight tag — no annotated/signed tag object)
**ctxcop integration surface:** `betterleaks/detect` (`Detector`, `DetectString`, `MaxDecodeDepth`), `betterleaks/config` (`ViperConfig.Translate`, `DefaultConfig`, `Rule`, `Config`), `betterleaks/report` (`Finding`). Integration LoC under audit ≈ 5,566 non-test lines (`detect/`, `config/`, `report/` only). Repo total ≈ 24,493 non-test Go LoC.

**Scope:** This assesses one dependency's fitness for ctxcop's specific integration surface at one commit. Process observations below are point-in-time properties of the project's configuration, recorded because they bear on ctxcop's upgrade policy; they are not an assessment of any individual, and nothing here is a reported vulnerability in betterleaks. Where an upstream defect is referenced, it is one already filed and acknowledged publicly.

## TL;DR

**Recommendation: pin v1.2.0 with four added mitigations.** Source-level review is clean; principal risks are upstream-process (single-maintainer, unreviewed merges, lightweight tags). Existing ctxcop mitigations (go.sum content pinning, embedded ruleset, deliberate avoidance of network/exec packages) substantially neutralize them.

## 1. Maintainer posture

**Project governance:** Single primary maintainer, continuous with the upstream `gitleaks` lineage — the fork dates to February 2026, following a governance dispute over the upstream repository. Bus-factor is effectively 1. Confidence: **verified**.

**Commit cadence:** First commit `25a02269` on 2026-02-03; v1.2.0 cut 2026-05-08. ~299 commits across 14 contributors in ~3 months, roughly half authored by the primary maintainer, with a long tail of one-to-few-commit contributors. Confidence: **verified**.

**Commit signatures:** Every commit reviewed (top 50 + spot-check across the v1.2.0 release range) returns `verified: true` with `reason: valid` from GitHub's signature verifier. Web-merged commits sign with GitHub's web-flow key; local commits use a PGP key whose public half isn't exposed via the public GPG-keys endpoint, but GitHub-side verification succeeds on every commit inspected. Confidence: **verified** for signature validity, **inferred** for key-to-identity binding (relying on GitHub's verification chain).

**Tag signing:** **v1.2.0 is a lightweight tag, not annotated.** `git cat-file -t v1.2.0` returns `commit`, and `git tag -v` errors with `"cannot verify a non-tag object of type commit"`. The release GitHub API returns `object.type: "commit"`. No signed tag object exists. The release artifacts are nominally protected by the signed HEAD commit at `296fee3`, but the v1.2.0 *tag pointer* itself is unsigned and could theoretically be re-pointed without breaking commit signatures (mitigated by GitHub's "immutable releases" feature, which the API confirms is enabled: `"immutable":true`). Confidence: **verified**.

**PR review:** Of the 22 PRs merged into v1.2.0, virtually all show `requested_reviewers: []` and `review_comments: null`, and merge latency is frequently short. The PR reviews endpoint surfaces only bot reviews (`greptile-apps[bot]`, `copilot-pull-request-reviewer[bot]`); no human reviewer approvals appear anywhere in the merged set, including on external contributions. Practical effect: merges are not gated on independent human review. Confidence: **verified**.

**Compromise history:** No public reports of maintainer-account compromise found via GitHub issues, security advisories, or web search. Confidence: **inferred** (absence of evidence).

## 2. Repo hygiene and supply chain

**Branch protection on `main`:** `gh api repos/betterleaks/betterleaks/branches/main/protection` returns 404 with a non-admin token. Consistent with **no public branch protection rule**, though it could also reflect a rule with insufficient read permissions. Combined with the absence of human review approvals noted above, the practical answer is **a single maintainer push can land code without independent review**. Confidence: **verified** (the review-gap evidence holds regardless of the protection-rule question).

**Tag signing / release signing:** v1.2.0 release artifacts are accompanied by `checksums.txt` (sha256, GoReleaser-generated, content verified by fetch) but **no cosign/sigstore signatures and no detached PGP signatures**. **Issue #134** — open, bug-labeled — documents that v1.2.0's GitHub-issued attestations were generated by a **private** workflow run and signed by GitHub's internal CA, so `gh attestation verify` fails ("Sigstore verification failed: verifying with issuer 'GitHub, Inc.'"). The artifacts cannot be verified against the public Rekor transparency log. This was acknowledged upstream and fixed in v1.3.0 (per the issue thread) using cosign via goreleaser, but **v1.2.0 itself remains unverifiable through standard sigstore tooling**. Confidence: **verified**.

**CI:** A single workflow, `.github/workflows/test.yml`, runs `go build` and `go test ./... --race` on ubuntu-latest and windows-latest. Notably, it pins third-party actions by commit SHA (`actions/checkout@de0fac2…`, `actions/setup-go@4b73464…`) — a positive supply-chain hygiene signal. **No CodeQL, no gosec, no govulncheck workflow.** Upstream `gitleaks/gitleaks` ships `gitleaks.yml`, `release.yml`, `test.yml` — also no CodeQL, so betterleaks did not drop CodeQL (it never had it). The release is built via goreleaser; PR #142 (post-v1.2.0) moved release builds into GHA. Confidence: **verified**.

**go.mod hygiene:** The direct dependency set is conventional (cobra, viper, zerolog, cel-go, aho-corasick, archives, go-github, go-cmp, testify, sprout). One concerning item: `go.mod` contains a `replace` directive redirecting `github.com/wasilibs/go-re2 v1.10.0 → github.com/betterleaks/go-re2 v0.0.0-20260402140350-…`. The fork is 18 commits ahead of upstream; the substantive change is a "minified" libre2 WASM blob (0 stars, single-maintainer fork). **However**, this only matters if the caller invokes `regexp.SetEngine(re2.RE2{})` — ctxcop does not, so the betterleaks/go-re2 fork (and its WASM blob) **never reaches ctxcop's binary**. `regexp/regexp.go:43` defaults to `Stdlib{}` (Go's standard `regexp`); only `cmd/root.go:154` flips to RE2 under a CLI flag. Confidence: **verified**.

Other transitive deps are reputable (Google, HashiCorp, fsnotify, Cobra/Viper ecosystem). No additional single-maintainer transitive deps observed in the integration-package import graph.

## 3. Code review at v1.2.0

I read or grepped every non-test `.go` file in `detect/`, `config/`, `report/`, `detect/codec/`, plus the transitively-imported `validate/` and `celenv/`.

**Network / exec / FS surface in integration packages:**
- `detect/detect.go:232` — `validationEnv.SetHTTPClient(&http.Client{Timeout: valOpts.Timeout})`. The HTTP client is only instantiated when `Validation` options are passed (ctxcop does not enable validation).
- `detect/baseline.go:38` — `os.ReadFile(baselinePath)` where `baselinePath` is set only by the CLI flag `--baseline-path`. ctxcop never sets it.
- `detect/detect.go:517` — `os.Open(gitleaksIgnorePath)` — same pattern, CLI-only.
- `report/template.go:24` — `os.ReadFile(templatePath)` — CLI flag only.
- **Zero `exec.Command`, zero raw `net.Dial`, zero `unsafe.*`, zero `//go:linkname` in `detect/`, `config/`, `report/`.** All exec calls live in `sources/git.go`, `sources/parallel_git.go`, `sources/scm/clone.go` — packages ctxcop does not import.

**Detection-bypass risk:** Searched for environment-variable-gated branches inside `detect/`, `config/`, `report/`. **None found.** The only env reads in the codebase are `cmd/root.go:245-248` (CLI flag fallback) and `cmd/github.go:71` (GITHUB_TOKEN for the github source). There is no `os.Getenv` or `os.LookupEnv` anywhere in the detection or config-translation hot path. A maliciously-crafted environment cannot tell `DetectString` to suppress results. Confidence: **verified**.

`detectFragment` (detect/detect.go:564) skips the configured `Config.Path` and `baselinePath` from scanning. Since ctxcop constructs `Config` in memory with `Path = ""` and never sets `baselinePath`, neither branch ever short-circuits a match.

**Codec / decode loop:**
`detect/detect.go:582-639` runs the decode loop with a strict `currentDecodeDepth > d.MaxDecodeDepth` bound. ctxcop sets `MaxDecodeDepth = 8`. `Decoder.Decode` (`detect/codec/decoder.go:24`) memoizes decoded values in a per-decoder map (`decodedMap`) — this is an exponential-blowup risk in theory, but the map is bounded by `len(unique encoded segments)` and the depth limit caps total passes. No recursion, no goroutines, no panics. `findEncodingMatches` (`detect/codec/encodings.go:135+`) is a single-pass byte scanner with no backtracking. `decodeBase64` (`detect/codec/base64.go`) only calls `base64.StdEncoding.DecodeString` / `base64.RawURLEncoding.DecodeString` and short-circuits via `isPrintableASCII`. **No panic statements anywhere in `detect/codec/`.** Confidence: **verified**.

**ViperConfig.Translate:**
`config/config.go:145-358`. Pure regex compilation + struct conversion + slice/map assembly. The only I/O risk is `c.extendDefault` / `c.extendPath` (`config/config.go:576+`), which read additional config files when the loaded config declares `extend.path` or `extend.useDefault`. ctxcop builds the `ViperConfig` from a compile-time embedded string and never sets `extend`, so the extension code is unreachable in our path. No `eval`, no `exec`, no `template.Execute` on user data, no reflection. Confidence: **verified**.

**Panics in library code:** `grep -rn 'panic('` in `detect/ config/ report/` (excluding `_test.go`) returns **zero results**. Confidence: **verified**.

**Unsafe / reflection / linkname:** Zero hits in the integration packages. Confidence: **verified**.

**`init()` functions:** Four, all in `detect/codec/{encodings,base64,ascii,hex}.go`. Each populates a 256-entry boolean lookup table. No I/O, no network, no global mutable state beyond the static tables. Confidence: **verified**.

## 4. Comparison to upstream gitleaks

Substantive divergences at v1.2.0:

- **Parallelized git scanning** (`sources/parallel_git.go`, new in betterleaks fork commit `bfaf8e2`). Not in ctxcop's path.
- **Buffer-pooled lowercase + aho-corasick prefilter** in `detectFragment` — performance optimization, sha256 of `detect/codec/decoder.go` (1b70c1b…) differs from upstream gitleaks decoder (5b41797…) because betterleaks added the memoized `decodedMap` and reorganized the loop. Behaviorally equivalent at the rule-match level. Positive divergence (faster, less GC pressure).
- **CEL-based filters and validators** (`celenv/` is a betterleaks invention) replacing the legacy allowlist mechanism. Major divergence — adds CEL-go and the `tetratelabs/wazero` runtime as dependencies. Filters compile but only execute against rules that declare them; ctxcop's rules do not, so the CEL hot path is dormant in our usage.
- **Token-efficiency filter** via bundled OpenAI `cl100k_base.tiktoken.gz` (775KB embedded asset). Adds tiktoken-go dependency. Activated only when a rule declares a `failsTokenEfficiency` filter.
- **`Run()` iterator API** + dynamic source attributes (PR #92). ctxcop doesn't use `Run`, only `DetectString`.
- **No security workflows removed** — gitleaks didn't have CodeQL either. Both projects ship `test.yml` + release tooling.

On balance, divergences are **functional additions** (better detection, more sources) rather than removals. No security-relevant gitleaks feature was dropped. Confidence: **verified**.

## 6. Risk assessment specific to ctxcop

**Worst-case scenario:** A backdoor inside `betterleaks/detect.DetectString` or `Decoder.Decode` that conditionally returns an empty `[]report.Finding` slice for adversarially-marked inputs. Because ctxcop runs the detector against tool output before that output reaches Claude's context window, a successfully-poisoned detector would mean an attacker who can influence tool output (e.g., a crafted file in the workspace, or a malicious MCP response) could smuggle credentials into Claude's context unredacted. The detection layer is the integrity boundary for the whole tool.

**Realistic likelihood:** **Low** for the v1.2.0 cut specifically, **moderate over time**. Evidence:

- 5,566 LoC under audit, all paths reviewed for env-gated branches, panics, network, exec, and unsafe — none found.
- Maintainership is long-established, with a multi-year history maintaining the upstream tool.
- Every commit at v1.2.0 verified-signed via GitHub.
- ctxcop's integration surface deliberately uses only the deterministic, pure-Go paths (`DetectString`, `Translate`, in-memory rules) and never touches the network/exec-heavy `sources/`, `celenv/http`, or `validate/pool` packages.
- However: single-maintainer governance with no human PR review and no branch protection means a future malicious commit could land in production within minutes. The audit is point-in-time on the v1.2.0 SHA.

**Existing mitigations sufficiency:** ctxcop's documented mitigations in `THIRD_PARTY_AUDIT.md` — pinning by go.sum, vendoring readiness, fork-readiness plan, embedded compile-time ruleset — address the principal failure modes:

- A poisoned `betterleaks.toml` cannot reach a deployed binary because ctxcop's rules are compiled in (verified: `config/betterleaks.toml` is loaded via `//go:embed` at `config/config.go:23-24`; ctxcop doesn't invoke `NewDetectorDefaultConfig`).
- go.sum pinning prevents an attacker who controls the betterleaks GitHub from substituting the v1.2.0 SHA without breaking go module verification.
- The v1.2.0 attestation defect (issue #134) is not a defense-relevant exposure for ctxcop builds, because ctxcop consumes the source via `go mod` against the commit SHA, not via the release tarball whose attestation is broken.

**Additional mitigations recommended:**

1. **Pin by commit SHA, not tag**, in `go.mod` if Go tooling allows — the v1.2.0 tag is lightweight and theoretically mutable; `go.sum` pins the content hash, which is what actually matters. Document this explicitly.
2. **Add a recurring fork-or-vendor trigger**: re-verify the v1.2.0 SHA matches our `go.sum` content at every ctxcop release build. Trivially scriptable.
3. **Track issue #134's resolution** before pinning any future betterleaks version that ships with sigstore attestations — verify them before consuming.
4. **Add a CI check** that fails ctxcop's build if `detect/`, `config/`, `report/` ever start importing `os/exec`, `net/http`, `unsafe`, or `reflect` (today they don't; a regression would be a strong signal).

## Recommendation

**Pin v1.2.0 with the four mitigations above.** The point-in-time review of the integration-package source is clean: no backdoor patterns, no env-gated bypasses, no panics, no exec, no unauthenticated network calls on the hot path. Commits at the audited SHA are consistently signed.

The principal weaknesses — single-maintainer governance, no human PR review, no branch protection, lightweight (unsigned) release tags, and broken sigstore attestations at v1.2.0 — are real but **upstream-process** risks rather than code-state risks at the audited SHA, and they are largely neutered by ctxcop's go.sum content pinning, embedded ruleset, and deliberate avoidance of the network/exec-heavy packages. Concretely, the realistic threat is not v1.2.0 being malicious now; it's a future malicious release landing fast under the same governance. The four mitigations above pin that risk to *our* upgrade cadence, where we control the review.

**Do not pin v1.2.0 binaries from GitHub releases for redistribution** (the sigstore attestations are unverifiable per issue #134). Source consumption via `go mod` against `296fee33358904c47d094fa6716347b223b2c13f` is acceptable.
